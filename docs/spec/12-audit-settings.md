# 12. Журнал действий и настройки

Статус: todo

Ветка: `step/12-audit-settings`
Навыки: `backend-development`, `secure-coding`, `ui-ux-design`

## Цель

Владелец видит, кто и что делал, и сам управляет залом: название, номер WhatsApp, сотрудники и их роли.

## Что входит

- `/audit` (только `owner`): лента событий (кто, когда, действие, ссылка на сущность по UUID), фильтр по сотруднику, действию, дате; пагинация по курсору.
- Единый хелпер `writeAudit(db, actor, action, entity, id, details)` и проверка, что все мутирующие сервисы его вызывают (перечень действий из ТЗ: оплата, сторно, изменение клиента, архив, удаление, изменение шаблона, вход).
- `/settings` (только `owner`) — единый раздел «Настройки» (D-11), всё, что владелец может захотеть поменять, в одном месте, разделами:
  - «Зал»: название, номер WhatsApp зала (нормализация `+77XXXXXXXXX`).
  - «Группы и цены»: список групп с ценой, тренером и расписанием; добавить, изменить, архивировать открывает ту же форму, что в шаге 05 (одна форма, без дублирования логики).
  - «Напоминания»: за сколько дней напоминать и тексты шаблонов на одном экране, с предпросмотром на реальном клиенте (форма из шага 09).
  - «Сотрудники»: `/settings/staff` (ниже).
- Правила удобства для «Настроек»: обычные слова вместо терминов (не `before_7`, а «Первое напоминание»), подсказка под каждым полем, значение по умолчанию видно, сохранение одной кнопкой с подтверждением «Сохранено», ошибки рядом с полем и понятным языком.
- `/settings/staff`: список сотрудников, добавление (email + имя + роль; приглашение через Supabase Auth admin API с `service_role` на сервере), смена роли, деактивация (доступ теряется сразу), запрет деактивировать последнего `owner`.
- Экран «Ещё» на мобильном: ссылки на напоминания, отчёты, журнал, настройки (по ролям), тема, выход.

## Что не входит

Изменение собственных данных сотрудника, кроме пароля.

## Критерии готовности

1. Интеграция: каждое мутирующее действие сервисов создаёт запись audit без ПД в `details` (тест перебирает действия).
2. Интеграция: нельзя деактивировать или понизить последнего `owner`.
3. Интеграция: деактивированный сотрудник сразу теряет доступ к данным (RLS).
4. Интеграция: `admin` не читает `audit_log` и не меняет `settings`.
5. E2E owner: пригласить сотрудника, сменить роль, деактивировать.
6. E2E: «Ещё» у `admin` не содержит отчётов, журнала, сотрудников.
7. `service_role` не попадает в клиентский бандл (поиск по `.next/static`).
8. E2E owner (390 px): из «Настроек» изменить название зала, цену группы и дни напоминаний; изменения видны на экранах групп, оплаты (цена подставляется) и напоминаний.

# 15. Сотрудники по паролю, без писем

Статус: done
Зависит от: 12, 13, D-14
Ветка: `step/15-staff-passwords`
Навыки: `backend-development`, `secure-coding`, `ui-ux-design`, `browser-verification`

## Цель

Сервис работает без почты (D-14): владелец сам задаёт сотруднику пароль и передаёт его лично, сотрудник при первом входе меняет пароль на свой. Письма, коды и ссылки из писем больше не нужны, SMTP не нужен.

## Что входит

- «Настройки → Сотрудники»: добавление сотрудника с полями имя, почта, роль, временный пароль (8–72 байта) вместо приглашения письмом. `auth.admin.createUser` с `email_confirm: true` на сервере, только `owner`, запись в журнал. Идемпотентность и гонки как в шаге 12.
- Владелец задаёт новый временный пароль существующему сотруднику («Сбросить пароль»), запись в журнал без самого пароля.
- Обязательная смена пароля при первом входе и после сброса владельцем: флаг в БД (например, `staff.must_change_password`), proxy пускает такого сотрудника только на `/update-password` и выход; после смены флаг снимается. Флаг меняет только сервер, не сам сотрудник через API (RLS, тест отказа).
- Страница входа: убрать «Забыли пароль?» и маршруты `/reset-password*`, страницу `/auth/confirm` оставить только если она ещё нужна (решить по коду), иначе удалить вместе с шаблонами писем.
- Тексты в `src/i18n` (русский; казахский и узбекский добавит шаг 16).
- Обновить `docs/runbook.md` (раздел 2.1 п. 4–5 про письма и SMTP больше не нужен) и `CLAUDE.md`.
- Сотрудник «Суннат» (почта и роль от владельца) добавляется уже через новый экран.

## Что не входит

Почта в любом виде. Вход по телефону. Двухфакторная защита.

## Критерии готовности

1. Владелец добавляет сотрудника с паролем, сотрудник входит, его сразу перенаправляет на смену пароля, после смены он попадает на «Сегодня».
2. Пока пароль не сменён, любой другой маршрут и любой Server Action отказывают (проверка на сервере, не скрытие кнопок).
3. `admin` не может добавлять сотрудников и сбрасывать пароли (интеграционный тест отказа и e2e).
4. Пароль нигде не логируется и не попадает в журнал, URL, тексты ошибок.
5. На странице входа нет «Забыли пароль?», маршруты сброса пароля отвечают 404.
6. `pnpm check` зелёный, проверка в браузере на 390 и 1440 px, `/security-review`.

## Результаты

- Флаг `staff.must_change_password` (миграция `staff_passwords`). Пока он включён, `current_staff_role()` возвращает `null`: все политики RLS и функции отказывают на уровне БД, а не только в приложении. Proxy и вход читают `current_staff_access()` (роль и флаг), proxy пускает только на `/update-password` и выход, `requireStaff` перенаправляет туда же. У `authenticated` нет права на колонку флага, флаг ставят `add_staff` и `begin_password_reset` (только владелец), снимает `complete_password_change` (только `service_role`, вызывает сервер после того, как Auth принял новый пароль).
- «Сбросить пароль» завершает все сессии сотрудника (`auth.sessions`), старый пароль сразу перестаёт работать. Себе владелец пароль здесь не сбрасывает (`self_change`).
- Журнал: `staff.invite` теперь называется «Добавлен сотрудник», новое действие `staff.password_reset` «Владелец задал временный пароль». Пароли не попадают в журнал (тест `audit-coverage` ищет оба пароля в строках журнала), в URL, логи и тексты ошибок: ответы сервера содержат только коды и имена полей.
- Длина пароля проверяется в байтах (до 72, ограничение bcrypt), не в символах.
- Удалены `/reset-password*`, `/auth/confirm`, шаблоны писем, Redirect URLs и Mailpit из CI и тестов. Под входом эти адреса отвечают 404; гость попадает на вход, как с любого неизвестного адреса (так не видно, какие маршруты существуют). Это отступление от буквы критерия 5.
- Проверка в браузере (production-сборка, 390 и 1440 px, светлая и тёмная тема): сценарий добавления, вход с временным паролем, переход на `/clients` возвращает на `/update-password`, смена пароля ведёт на «Сегодня»; диалог сброса закрывается по Esc; горизонтальной прокрутки нет, области нажатия от 44 px, ошибок и предупреждений в консоли нет. Скриншоты в `screenshots/15/`.
- Lighthouse mobile (локальная production-сборка, `simulate`): `/login` 98 / 100 / 100, LCP 2,4 с; `/settings/staff` 94 / 100 / 100, LCP 3,0 с; `/update-password` 97 / 100 / 100, LCP 2,6 с; CLS 0. JS первой загрузки: `/login` 146,0 КБ, `/settings/staff` 147,8 КБ.

- Сотрудник «Суннат» (роль администратор, почту назвал владелец): добавляет владелец на production через «Настройки → Сотрудники» после деплоя этого шага, с временным паролем, который передаёт лично. Пароль владельца у разработчика нет и быть не должно; почта в репозиторий не записывается (ПД).
- Security review: уязвимостей не найдено. Отмечено как вопрос к заказчику, не дефект: владелец может задать временный пароль другому владельцу и войти под ним (запись в журнале, у второго владельца перестаёт работать пароль). Раньше владелец уже мог понизить или отключить другого владельца.
- Локальный `pnpm check`: типы, линтер, формат, unit 598, интеграция 502, сборка зелёные; локальные e2e нестабильны под нагрузкой (таймауты БД `57014` в чужих сценариях), решающий прогон в CI.

## Заметки на будущее

- Ссылки на добровольную смену пароля в интерфейсе нет: `/update-password` работает, но открыть его можно только по адресу. Место для ссылки: экран «Ещё».
- Забытый пароль владельца по D-14 меняет разработчик скриптом. Такого скрипта ещё нет (`owner:create` создаёт только первого владельца). Пока выход один: второй владелец сбрасывает пароль в «Настройках».
- Параллельные одинаковые запросы «Добавить сотрудника»: Auth создаёт одного пользователя, проигравший запрос получает `email_exists` или 500 (тогда ответ «не удалось сохранить»). Итог верный, текст для второго запроса можно уточнить.
- В production Supabase остался Redirect URL `/auth/confirm` и значение `additional_redirect_urls` из шага 13, убрать при следующем `config push` (runbook 2.1).

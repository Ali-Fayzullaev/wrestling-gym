# CLAUDE.md

Внутренний веб-сервис учёта абонементов зала вольной борьбы (Шымкент): клиенты, группы, оплаты, напоминания через wa.me.
Спецификация: [docs/spec/00-overview.md](docs/spec/00-overview.md). Открытые решения заказчика: [docs/spec/90-open-decisions.md](docs/spec/90-open-decisions.md). Исходное ТЗ: [docs/prompt.md](docs/prompt.md).

## Главные правила

1. Не придумывать решения заказчика (D-01…D-10). Нет решения: не реализуем или делаем заглушку с комментарием `// STUB(D-NN): ...` и строкой в `90-open-decisions.md`.
2. Без эмодзи нигде: код, интерфейс, коммиты, документы. Иконки только `lucide-react`.
3. WhatsApp только через ссылку `https://wa.me/<номер>?text=...`. Никаких API, ботов, неофициальных сервисов. «Чат открыт» не значит «отправлено», интерфейс так и пишет.
4. Оплаты, сторно, согласия и журнал действий только добавляются. Запрет UPDATE/DELETE закреплён в БД (RLS + триггер).
5. Идемпотентность закреплена уникальным ключом в БД (`payments.idempotency_key`, `reminder_events (payment_id, kind)`), а не только проверкой в коде.
6. RLS включён на каждой таблице. Для каждой политики есть тест «чужая роль получает отказ».
7. Персональные данные (имена, телефоны) не попадают в логи, URL, аналитику, тексты ошибок. В URL только UUID.
8. Время: «сейчас» передаётся в бизнес-логику параметром. Даты считаем в `Asia/Almaty` (UTC+5).

## Один чат — один шаг

Каждый чат выполняет ровно один шаг из `docs/spec/NN-*.md`. Закончил шаг: отчёт и промпт для следующего чата, дальше не идём. Подробности в навыке `spec-step`.

## Порядок выполнения шага

1. Прочитать файл шага и `90-open-decisions.md`. Проверить, что зависимости шага в статусе `done`.
2. `git switch main && git pull && git switch -c step/NN-name`.
3. Статус шага: `in-progress`.
4. Код вместе с тестами. Баг: сначала падающий тест, потом исправление.
5. Проверка в браузере на 390 и 1440 px (навык `browser-verification`).
6. `pnpm check` зелёный (типы, линтер, формат, unit, интеграция, e2e, сборка).
7. `/security-review`, если шаг затрагивает данные, доступ или вход.
8. Проверить diff на секреты: `git diff --cached | grep -iE "service_role|secret|password|eyJ"` пусто.
9. Обновить статус и чек-лист шага, статус в таблице `00-overview.md`.
10. Коммит на английском: `feat(step-06): add client filters` (типы: feat, fix, test, docs, chore, refactor, perf).
11. Пуш, PR в `main`, дождаться зелёного CI.
12. Отчёт и промпт для следующего чата.

## Тесты обязательны

- Нет теста, значит шаг не завершён.
- Тесты не отключать, не помечать `skip`, не ослаблять утверждения, чтобы стало зелёно.
- Проверять отказы: нет доступа, неверный ввод, повтор запроса, параллельные запросы.
- Интеграционные тесты идут против настоящей локальной БД (`supabase start`), без моков Supabase.
- Unit: Vitest. E2E: Playwright, проекты `mobile` (390 px) и `desktop` (1440 px).
- Часы в тестах фиксированные: функции принимают `now: Date`.

## Структура и направление зависимостей

```
src/
  app/                 маршруты, layout, loading.tsx, Server Actions (тонкие)
  features/<область>/  service.ts (бизнес-логика), schema.ts (Zod), components/, *.test.ts
  lib/                 общие утилиты без бизнес-логики (даты, деньги, телефон, wa.me)
  db/                  клиенты Supabase, сгенерированные типы
  i18n/                все тексты интерфейса (ru; kk позже, D-04)
  components/ui/       компоненты shadcn/ui (не импортируют app и features)
supabase/migrations/   SQL-миграции, единственный источник схемы
tests/integration/     Vitest против локального Supabase
tests/e2e/             Playwright
tests/lint/            тесты правил ESLint (границы слоёв, any)
docs/spec/             шаги и решения
```

Зависимости только вниз: `app` → `features` → `lib`, `db`. `features` не импортируют `app`; `lib` не импортирует `features`.
`service.ts` принимает клиент БД и `now` параметрами, не импортирует ничего из `next/*`.
Server Action: сессия → роль → Zod → вызов сервиса → `revalidatePath`. Права проверяются на сервере, скрытие кнопок не защита.

## Качество кода

- TypeScript strict. Без `any`, `@ts-ignore`, `as unknown as`. Нестандартный случай: `@ts-expect-error` с причиной.
- Маленькие функции с одной задачей. Имена говорят, что делает функция.
- Комментарий объясняет почему, а не что.
- Без мёртвого кода, закомментированных блоков и абстракций про запас.
- Новая библиотека только при явной необходимости, с обоснованием в PR. API библиотек сверять с актуальной документацией (MCP `context7`, если подключён; иначе официальная документация).
- Тексты интерфейса только из `src/i18n`.

## Скорость в каждом изменении

- Цели на мобильном 4G: LCP < 1,5 с, INP < 100 мс, CLS < 0,05. JS первой загрузки на маршрут ≤ 150 КБ gzip (`pnpm build`).
- Экран делает не больше 2–3 запросов к БД, без N+1. Статусы и счётчики считаются в Postgres.
- Server Components по умолчанию; `"use client"` только для интерактива.
- `loading.tsx` со скелетоном на каждом маршруте. Оптимистичные обновления для «Оплатил».
- Тяжёлое (xlsx, парсинг) только на сервере.

## Минимум безопасности в каждом изменении

- Новая таблица: RLS включён, политики, тест отказа для чужой роли.
- Ввод проверен Zod на сервере. Ошибки пользователю без ПД и без внутренних деталей.
- `service_role` только в серверном коде, никогда в `NEXT_PUBLIC_*`.
- `.env*` в `.gitignore`, секреты в Vercel и GitHub Secrets.

## MCP

| MCP | Назначение |
| --- | --- |
| `supabase` | Схема, логи, advisors, документация dev-проекта |
| `vercel` | Деплои, логи, переменные окружения |
| `context7` | Актуальная документация библиотек |
| `playwright` | Проверка интерфейса в браузере |

Правило для `supabase` и `vercel`: только чтение и работа с dev-проектом. Production меняется только миграциями из репозитория и деплоем из CI. Прямые правки production (SQL, env, домены) только по явной просьбе владельца.
